# 05.1 - BACKUP PROCEDURES

A backup is useful only if it contains the needed data and can be restored. Keep at least
one copy on a separate device, protect it from unauthorized access, and periodically test
restoring it.

## What the application backup contains

The manager dashboard's **Settings → Backup & Restore** area can create and download an
archive. The backup service includes the SQLite database, available menu/feedback images,
logs, backend `.env` / `.env.local`, and uploads where present. Treat the archive as
sensitive: environment files can contain credentials.

Cloud upload is conditional, not guaranteed:

- The backend must be running at the scheduled time. It schedules a daily run for 3:00 AM
  in the server's local time zone and checks for a missed backup at startup.
- Valid Backblaze B2 configuration is required.
- `BACKUP_ENC_KEY` is required for cloud upload; the service refuses to upload an
  unencrypted cloud archive. Without it, a local archive may still be created without
  encryption.
- Failures are written to backend logs. A scheduled time or a success-shaped dashboard
  message is not proof that the latest archive exists and is restorable.

Check **Settings → Backup & Restore** for the listed backups and confirm a newly created
backup can be downloaded. Keep `BACKUP_ENC_KEY` in a separate secure password manager or
other protected location. Losing that key can make encrypted backups unrecoverable. Do not
store the key beside the encrypted archive.

## Create a manual backup before maintenance

1. Avoid taking orders while the backup is in progress.
2. Stop the application so SQLite is not being written:
   - Raspberry Pi service: `sudo systemctl stop dragonfly-garden`
   - Windows: sign in as manager, choose **Settings → Server control → Stop backend
     for everyone**, and wait until `http://127.0.0.1:5000/health` no longer responds.
3. Use the matching script in [`SCRIPTS`](SCRIPTS):
   - Linux: `bash Documentations/SCRIPTS/create-full-backup.sh`
   - Windows: run `Documentations\SCRIPTS\create-full-backup.bat`
4. The script writes the dated data archive outside the repository to
   `~/DragonflyBackups` on Linux or `%LOCALAPPDATA%\DragonflyBackups` on Windows. It does
   not include `.env` or `.env.local`; store credentials separately in a password
   manager. Copy the archive to a separate, access-controlled drive. Do not email it or
   upload an unencrypted archive to a public/shared service.
5. Restart the application and verify it is healthy.

The script expects to be run from its checked-out project and stops if the default
application port is still listening. If the server uses another port or a different
service setup, confirm the application is fully stopped before backing up.

## Protect and verify backups

- Keep encrypted backups and their encryption key in separate protected locations.
- The manager's local archive can contain plaintext environment secrets when
  `BACKUP_ENC_KEY` is absent. Restrict access and do not share that archive.
- Keep multiple dated copies; a newer backup may already contain an error or unwanted
  changes.
- Periodically use a test machine or a planned maintenance window to restore a copy and
  verify the database, images, login, and printer. A file existing is not proof of a
  successful restore.

See [05.2-RESTORE_PROCEDURES.md](05.2-RESTORE_PROCEDURES.md) before restoring. The Linux
script creates `.tar.gz`; the Windows script creates `.zip`. Both include the database
and any SQLite WAL sidecar files present when the stopped database is copied. Do not use
the old `restoreBackup.js` emergency command; it is incompatible with the current encrypted
archive format.
