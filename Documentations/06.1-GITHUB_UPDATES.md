# 06.1 - UPDATE FROM THE PROJECT'S GIT REPOSITORY

An update changes application code. It should not replace the restaurant database or
machine-specific configuration. Back up the data first and do not update during service.

## Manager dashboard update

1. Make and verify a backup using [05.1-BACKUP_PROCEDURES.md](05.1-BACKUP_PROCEDURES.md).
2. Before enabling automatic updates, obtain the maintainer's full GPG signing-key
   fingerprint through a separate trusted channel, import that maintainer's verified
   public key into the account that runs the backend, and add the fingerprint to
   `UPDATE_TRUSTED_COMMIT_SIGNERS` in `restaurant-system/backend/.env`. Keep this
   allowlist limited to project release signers. Release commits must be GPG-signed and
   pass `git verify-commit`; otherwise the in-app updater blocks them.
3. Stop taking orders and payments. Confirm the configured Git remote (`origin`) and
   update branch are the intended release source. The branch is `UPDATE_BRANCH`, or
   `main` if that setting is not configured.
4. In the manager dashboard, open **Settings → System Updates** and choose **Check for
   Updates**. Review the current and available commit IDs and the eligibility message.
5. Continue only when the dashboard says the update is ready. The manager must confirm
   the reviewed commit. The updater then creates a temporary worktree, installs from
   lockfiles there, runs backend tests, and builds the frontend. The installed code is
   fast-forwarded only if those checks pass and the installation has not changed.
6. Follow the restart instructions shown after success. On Raspberry Pi, restart the
   service with `sudo systemctl restart dragonfly-garden`. On Windows, use **Settings →
   Server control** to stop the backend, then open the Manager desktop shortcut.
7. Before resuming service, verify the health endpoint, manager login, saved data, and a
   physical test receipt.

The in-app updater does not modify restaurant data or `.env`, does not run database
migrations, and refuses updates that alter backend dependency manifests. It also refuses
dirty worktrees, non-fast-forward branches, project `.npmrc` files, unsigned/untrusted
commits, and a remote commit that changed after review. Staging commands do not inherit
the running backend's environment variables, but execute as the same operating-system
account and are not sandboxed. Only sign and trust release code you have reviewed.
If any check fails, no update is applied; read the displayed reason and use the manual
procedure below only after preserving local work.

## Manual procedure (blocked or offline updates)

1. Make and verify a backup, stop taking orders, and stop the backend:
   - Raspberry Pi: `sudo systemctl stop dragonfly-garden`
   - Windows: sign in as manager, choose **Settings → Server control → Stop backend
     for everyone**, and wait until `http://127.0.0.1:5000/health` no longer responds.
2. Open a terminal in the project root and check the branch, worktree, and remote:

   ```text
   git status --short
   git branch --show-current
   git remote -v
   ```

   Continue only if the worktree is clean, the branch is intended, and `origin` is the
   expected repository. Do not delete, reset, or overwrite local changes to make it clean.

3. Update source code with a fast-forward-only pull:

   ```text
   git pull --ff-only
   ```

4. The manual procedure does not provide the in-app updater's signature gate. Use it only
for a complete release independently verified through a trusted channel. If backend
dependency manifests changed, install backend dependencies using
   `npm ci` in `restaurant-system/backend`. Run `npm test` there. In `frontend`, run
   `npm ci` followed by `npm run build`. If any command fails, do not continue as though
   the update succeeded; keep the error output and resolve it before restarting.

## Start and verify

- Raspberry Pi systemd installation (if it was stopped):

  ```bash
  sudo systemctl start dragonfly-garden
  sudo systemctl status dragonfly-garden --no-pager
  curl -i http://127.0.0.1:5000/health
  ```

- Windows laptop: open the Manager desktop shortcut, or run
  [`START_DRAGONFLY_GARDEN.bat`](../Start%20the%20app%20in%20deployment%20form/Pc/START_DRAGONFLY_GARDEN.bat)
  to start the backend in the background and open the manager view.

Before resuming service, log in, inspect the menu and existing data, and print a test
receipt. A running process or HTTP health response does not by itself verify the printer
or all business workflows.

If a failed manual update needs rollback, stop the server and use a known-good code
revision and verified data backup. Do not use `git reset --hard` on a machine that may
contain local work or production data.
