# 05.2 - RESTORE PROCEDURES

Restoring replaces application data. Choose the correct dated backup before proceeding
and preserve the current database first. Do not restore while the app is accepting orders.

## Restore through the manager dashboard

Use this method when the current application can start and a manager can log in:

1. Create/download a fresh backup of the current data if possible.
2. Open **Settings → Backup & Restore**.
3. Select the intended local or cloud backup, or upload a supported backup archive.
4. Read the confirmation and verify the selected backup name/date before confirming.
5. Wait for the restore result. Do not close the app or interrupt the server while the
   database is being replaced.
6. Verify login, menu, employees, settings, images, and a printer test before reopening
   for service.

The application has separate restore paths for listed cloud backups, local backups, and
uploaded archives. Availability depends on a valid archive, B2 credentials for cloud
access, and (for encrypted archives) the correct `BACKUP_ENC_KEY`. A cloud listing alone
does not verify that a backup can be decrypted or restored.

The manager's archive restore code also copies `.env` and `.env.local` from an archive
when those files are present. On a different computer, this can replace that computer's
host-specific settings. Before restoring to another host, save its configuration
separately; after restore, review/recreate the target `.env` and `.env.local` and verify
`JWT_SECRET`, network settings, and optional integration credentials before restarting
or accepting orders.

## Restore a manual archive if the dashboard is unavailable

The included Linux backup script creates a dated `.tar.gz` archive; the Windows script
creates a `.zip`. Both contain the database and available data files. For safety, the
`restore-from-backup` helper scripts are disabled;
their old versions could overwrite the wrong data or stop unrelated Node processes.

If the dashboard cannot be used, do not run `node src/restoreBackup.js`. That legacy
script downloads a cloud object and writes it as a SQLite database, but current cloud
backups are encrypted archives, not raw database files. It can corrupt the database.
Recover via a verified local archive with an experienced operator:

1. Stop the backend service/process completely and confirm it is stopped.
2. Make a separate copy of the current database and image folders.
3. Inspect the archive contents before extracting it. Only use an archive created by the
   project's backup script or manager backup flow and stored in a trusted location.
4. Extract to a temporary directory, not over the project.
5. Verify the archive contains a plausible `database.sqlite`. Restore the database and
   any archived `database.sqlite-wal` / `database.sqlite-shm` sidecars together into
   `restaurant-system/backend/src/database/` while the server is stopped. Preserve the
   current database and sidecars before replacing them. Restore image folders only if
   needed.
6. Keep the existing machine's `.env` unless you have deliberately reviewed every
   setting. Never blindly replace a new machine's `.env` with one from another host.
7. Start the server and verify the data and printer before accepting orders.

Do not restore the systemd service file from another host without reviewing its username,
paths, and Node executable. Restore is destructive by nature; if you are unsure which
backup or files to use, stop and get help rather than guessing.

## Set up another computer

For a new laptop, install the code and dependencies first, create a machine-specific
`.env`, then restore only the intended data. Do not use continuous database copying as
sync; see [05.3-SYNC_BETWEEN_DEVICES.md](05.3-SYNC_BETWEEN_DEVICES.md).
